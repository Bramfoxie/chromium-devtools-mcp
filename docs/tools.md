# Tools

Every tool with its behavior. Element targeting is in [frames-and-shadow-dom.md](frames-and-shadow-dom.md), limits in [output-limits.md](output-limits.md), safety gating in [safety.md](safety.md).

## Tabs and sessions

- `list_sessions`: list open sessions of the daemon without their tab details. Each session shows the client name the MCP client sent in its initialize request, or `chromium-devtools-mcp` when it sent none.
- `list_tabs`: list the tabs of the session, or with `scope: "available"` the tabs it can claim. Each tab has its id, `url`, `title`, `owned`, `created` and, for owned tabs, `selected`. `limit` defaults to 100 (maximum 500); `total` counts the tabs in the scope and `truncated` tells whether the limit dropped some.
- `select_tab`: select an owned tab, claiming an available one when needed. Never focuses it.
- `new_tab`: open a background tab and select it. With a `url` it waits for the page to commit and load, for at most `timeoutMs` (default 30000), and returns the committed `url` and `title`, `waited` (`load`, `timeout` or `none`), the document `readyState` and the HTTP `status` when observed. A download, an empty 204 response or a network error does not fail the call: the tab stays open, on `about:blank` for a download or a 204 and on the browser error page for a network error, and `navigationError` says why. The tab is never brought to the front.
- `close_tab`: close a tab opened by this session.
- `bring_to_front`: bring a tab and its window to the front and take the keyboard focus. It is the only tool that does, and it works only when `allowFocus` is on (off by default); otherwise it refuses and says so. It acts on the given tab or the selected one, does not change the selection, and in read-only mode or on a tab outside `safety.allowedDomains` it is refused like other state changing tools. Use it only when the user asked to see the tab.
- `page_info`: read the URL, title, viewport, scroll position and emulation state of a tab.
- `page_navigate`: open a URL, go back or forward, or reload, waiting for the page to load. Back and forward refuse a history entry that is not an http, https or about:blank page.

## Inspection and navigation

- `js_evaluate`: run JavaScript in a tab. Page exceptions come back as data, not as tool errors. The exception text and the value are cut at `maxResultChars` with a marker; a value that cannot be serialized within the 32 MiB protocol limit is reported as its description with `truncated: true`.
- `dom_query`: find elements by a CSS selector and read their text, attributes and boxes.
- `dom_snapshot`: read a compact text snapshot of the page with element ids.
- `css_inspect`: read the computed style, matched CSS rules and box of an element. The result carries `totalRules`, `truncated` and `droppedWinners`, the properties whose winning declaration is in a rule that `maxRules` dropped.
- `click`: click an element at the DOM level with `element.click()` semantics. Works on covered elements and background tabs; the event is not trusted.

## Input

- `input_click`: click with trusted CDP mouse events, like a real user. Pass either a `target` element or a `point`, never both. With a `target` it refuses a covered element unless `force` is passed. A `point` is `{ x, y }` in CSS pixels from the top left corner of the viewport, which a vision based agent gets from a viewport `screenshot` by dividing the pixel of the image by the `pixelRatio` the screenshot reports (the image of a screen with a device pixel ratio of 2 is twice as wide as the page), so it can click what it sees. The events go to the tab at those coordinates, also over a cross-site frame, and no hit test is made: the result names the element under the point (an `iframe` for a frame) and omits `target` when nothing is there. A point outside the viewport is refused. `button`, `clickCount` and `modifiers` work for both; `position` and `force` are for a `target` only. With `safety.allowedDomains` a point inside a frame from another origin is refused, and so is a point whose frame cannot be identified.
- `input_hover`: hover an element with trusted CDP mouse events, so hover styles and menus react.
- `input_drag`: drag from one end to another and drop there with trusted CDP mouse events. Each end is an element (`uid` or `selector`, resolved and hit tested like `input_click`) or a viewport point `{ x, y }` in CSS pixels. The mouse is pressed at the start, moved to the end in `steps` moves (default 8, at most 50) and released there. It works for pointer based drags (sliders, sortable lists) and for HTML5 drag and drop: when the page starts a native drag, the tool completes it with the drag enter, over and drop events at the end, and `kind` says `html5`; otherwise `kind` is `pointer`. Both ends are resolved before the mouse is pressed, so the end point does not follow a layout that shifts during the drag. An element inside a cross-site frame is refused with a hint to pass a point; a point inside such a frame works for pointer drags. With `safety.allowedDomains` both ends are checked, and a failure releases the button.
- `input_type`: type text into a field, with `clear` and `submit` options. Passwords are typed but never echoed back.
- `input_key`: press a key or chord like `Enter` or `ControlOrMeta+C`. `ControlOrMeta` resolves from the browser platform. On macOS, Control combined with a letter does not trigger editing commands such as select all; use `Meta+A` or `ControlOrMeta+A` there.
- `input_scroll`: scroll by wheel deltas, to the top or bottom, or an element into view. Reports honestly when the wheel left the window position unchanged.
- `input_select`: choose options of a `select` by value, label or index.
- `input_upload`: attach local files to a file input. This is the most sensitive tool: it sends local files to a web page. Paths are validated on the server machine (absolute, existing regular readable files under 100 MiB, at most 20), symlinks are followed, and results carry file names and sizes only, never contents.
- `fill_form`: fill 1 to 30 form fields in one call, in order. Each field is a `target` and a `value`: a string for a text, email, password or textarea field (the field is cleared first, and an empty string only clears it), `true` or `false` for a checkbox (it is clicked only when its state differs), `true` for a radio button, and for a select an option value or label, or a list of them for a multiple select (each entry is matched by value first, then by label). It uses the same trusted typing and the same checks as `input_type`, `input_select` and `click`. It stops at the first field that fails, with an error that names the field and says which fields were filled and which were not attempted; the fields before it stay filled. The result lists the kind and effect of each filled field and never repeats a value, so passwords do not come back. File inputs go through `input_upload`. Every field is checked against `safety.allowedDomains` and refused in read-only mode, like the tools it is built from.

## Observation, control and storage

- `network_requests`: read HTTP requests of a tab with URL, method, resource type, status and failure filters.
- `network_response_body`: read the response body of a request from `network_requests`. Binary bodies need `asBase64`; without it the result has `needsBase64: true` and no body. `maxChars` defaults to 50000 and allows up to 500000; a base64 body is cut at a multiple of 4 characters and always keeps at least 4. Bodies over the 32 MiB transport limit are refused. Redirect responses have no body.
- `network_mock`: mock responses or fail requests by Fetch wildcard pattern (`*`, `?` and the `\` escape), with delay and a use count. First match in insertion order wins.
- `console_logs`: read console messages, uncaught exceptions and browser messages of a tab, with level and text filters, paging and clear.
- `page_dialogs`: see and resolve JavaScript dialogs, or set an automatic accept or dismiss policy for later ones.
- `page_wait`: wait for a selector, text, URL, load state or expression. A timeout returns `met: false`, not an error.
- `storage_read`: read local storage, session storage or cookies of the page origin. Values of all kinds are hidden by default: the result lists keys (or cookie names) with the value size and `includeValues: false`. Pass `includeValues: true` to read values.
- `storage_write`: write local storage, session storage or cookies of the page origin. Cookie domains must match the page host. `clear` needs `confirm: true`.
- `page_pdf`: print a tab to PDF with orientation, paper, margins and page ranges. Needs a headless managed browser when the headed browser refuses to print. The PDF defaults to 8 MiB and `maxBytes` raises that to 24 MiB; a larger PDF is refused with a hint to use `pageRanges`.
- `page_metrics`: read performance counters, layout metrics and navigation timing of a tab.
- `screenshot`: capture a tab as an image. Defaults to jpeg quality 80; supports viewport, full page, element and clip shots. The result reports `pixelRatio`, the pixels of the image per CSS pixel of the page, which is above 1 on a high density screen and changes with `scale`; divide a pixel of a viewport shot by it to get the CSS pixels that `input_click` takes.
- `list_devices`: list the built in devices for `emulate_device`, with an optional name or kind filter.

## Emulation

- `emulate_device`: emulate a device size, pixel ratio, mobile viewport, touch and user agent. The Chrome version in the user agent of a desktop or Android device follows the connected browser. Client hints metadata is not emulated.
- `emulate_media`: emulate a media type and media features such as color scheme and reduced motion. Only the given fields change, and reset: true cannot be combined with other fields.
- `emulate_network`: emulate network conditions with a preset (offline, slow-3g, fast-3g, 4g, wifi, none), custom latency and throughput (a throughput of 0 is rejected, use -1 to remove the limit), or blocked URL patterns. The none preset also clears blocked URLs, and reset: true cannot be combined with other fields. Shares `Network.enable` with the capture tools and never disables capture.
- `emulate_locale`: emulate locale, timezone and Accept-Language. Takes effect on the next page load: `navigator.language` changes after navigation, and number and date formatting follow the locale.
- `emulate_geolocation`: emulate the position of a tab and let the page origin read it without a prompt. It takes `latitude`, `longitude` and an optional `accuracy` in meters (default 10); `origin` defaults to the origin of the tab and is needed for a tab that shows no page yet, so the location can be set before the first navigation; `reset: true` removes the override and the permission. The result lists the emulation state and what the page reads now when the tab shows that origin. Chrome gives a position to secure contexts only (https or localhost), and the tool keeps focus emulation on so a background tab receives it too. The permission is given through the daemon, only for geolocation and only for that origin, so every other permission of the origin stays as it was; it is removed on reset, when the tab closes and when the session ends. It is a dangerous call: with `safety.confirmDangerous` the user is asked first, because in a shared browser (a session that is not isolated) the other tabs of that origin read the real position while the permission stands. It is refused in read-only mode and for an origin outside `safety.allowedDomains`, in the tool and again in the daemon. Cross-site frames of the tab get the same position override.

## Performance

- `perf_trace_start`: start recording a performance trace of a tab. With `reload: true` (and optionally `ignoreCache`) the page is reloaded once the trace has started, so the whole load is recorded; without it the trace records what happens next, for example the interactions you make. The browser records one trace at a time for every client, so a second start answers busy until the first one has stopped. Starting is a reading call, and with `reload` it counts as a change like `page_navigate`. The tab keeps rendering while it records, so a background tab produces paints.
- `perf_trace_stop`: stop the trace and return its results. The trace is saved as a JSON file in the Chrome trace format, which the Performance panel of Chrome DevTools opens, and the result gives its path and size. A trace is cut at 800000 events and says so with `truncated`. It reports the Core Web Vitals measured from the last navigation of the main frame: First Contentful Paint, Largest Contentful Paint with its element, Cumulative Layout Shift (the worst session window, ignoring shifts after input), Interaction to Next Paint (when the trace holds interactions; the 98th percentile once there are 50) and Total Blocking Time. It also gives the longest tasks over 50 ms, the self time of the main thread by activity (scripting, rendering, painting, loading, garbage collection, other), the number, failures and transfer size of the requests with the largest ones (secrets in their addresses are redacted), and an `insights` list in which each value is rated good, warn or poor against the Web Vitals thresholds.

- `heap_snapshot`: take a heap snapshot of a tab and report what is in memory: the total size and object count, the size by kind of object, the biggest groups by name, and the detached DOM nodes (nodes removed from the page that JavaScript still holds, listed by tag), with an `insights` list that warns about detached nodes and about a heap that is mostly strings. The page freezes while the snapshot is taken, and a garbage collection runs first unless `collectGarbage` is false, so only live objects count. A snapshot over 100 MiB is dropped. The summary never contains the contents of strings: strings, numbers and symbols are listed by kind only, and addresses are cut from names. With `save` (the default) the whole snapshot is also written as a `.heapsnapshot` file that the Memory panel of Chrome DevTools opens. That file holds everything in the memory of the page, including secrets such as tokens and passwords, so pass `save: false` when you want the summary only. It counts as a dangerous call unless `save` is false, so with `safety.confirmDangerous` you are asked first. A snapshot covers the heap of the renderer process of the tab, so tabs of the same site that share the process share the heap, and a cross-site frame has a heap of its own that is not included.

- `screencast_start`: start recording what a tab shows as a series of frames. `fps` (1 to 30, default 10) is the most frames per second, `quality` the JPEG quality of a frame (1 to 100, default 60), `maxWidth` the widest frame in pixels (100 to 3840, default 1280; wider pages are scaled down) and `maxDurationMs` the time after which the recording stops by itself (1000 to 120000, default 30000). The tab keeps rendering in the background and no window is raised. A frame is made only when the page changes, so a static page produces few frames. In a browser with a window Chrome slows the timers of a tab in the background to about one a second and stops its animation frames, so an animated page records few frames there; bring the tab to the front first (`bring_to_front` with `allowFocus`) to record it at full rate. A headless browser has no such slowdown. One recording runs per tab, and the recording ends at 3000 frames or 256 MiB.
- `screencast_stop`: stop the recording and save it. When `ffmpeg` is on the `PATH` of the server, the frames are encoded into one MP4 file, or into WebM when the MP4 encoder is missing, with the timing of the frames kept, and only that file is left. `ffmpeg` is not part of this package and nothing is installed for it: the server only runs the program that is already on the machine, without a shell and with fixed arguments. Without `ffmpeg`, or when it cannot encode the frames, the result is a directory with one JPEG file per frame and `frames.txt`, which lists each frame with its duration in the format of the ffmpeg concat demuxer, and the `note` says how to get a video (install `ffmpeg` and encode that list). The result gives the `format` (`mp4`, `webm` or `frames`), the `path` of the file or directory, its size, the number of frames and the length of the recording. A recording without any frame is an error.

- `lighthouse_audit`: audit a page with Lighthouse and report the scores of the categories and the failed checks. Lighthouse is not part of this package and nothing is installed for it: the tool runs the `lighthouse` program that is already on the `PATH` of the server (install it with `npm install -g lighthouse`, which needs Node.js 22.19 or newer). When it is missing the call fails with a message that tells the agent to ask the user to install it, and nothing else happens. `doctor` shows whether it is found. It audits `url`, or the page of the tab when no `url` is given, only for http and https pages. `categories` are `accessibility`, `best-practices` and `seo` by default; `performance` can be added, but `perf_trace_stop` measures performance on your own tab. `device` is `desktop` (the default) or `mobile`, and `timeoutMs` (10000 to 300000, default 120000) bounds the run, which usually takes 10 to 60 seconds. Lighthouse starts its own clean browser with a temporary profile (the browser the server found, headless), so it sees the page as a new visitor: it does not use the logins of your tabs, so a page behind a login is audited as its login page, and it does not touch your tabs. The result gives the scores from 0 to 100, the failed checks with the worst first (at most 15, each with up to 5 failing elements as selector and markup start, and `failedCount` for all), the number of passed checks, Lighthouse warnings, and the paths of the full report as JSON and as an HTML file that opens in a browser, both in the `artifacts` directory. The call counts as a change like `new_tab`: it is refused in read-only mode and for an address outside `safety.allowedDomains`, and the tab URL is checked too when no `url` is given. The arguments passed to the program are fixed and never go through a shell.

A trace covers the whole browser, so it would hold the addresses and labels of every other tab. The file and the numbers keep only the events that name nothing but frames of the tab, and the events of the processes that host those frames when they name no frame and carry no address, title, host or message. Events of the browser process are kept only when they name a frame of the tab, such as the commit of its navigation; the rest of the browser process, the GPU process and other renderers are left out, and so are the process labels, which hold tab titles, and the marks that page scripts write with the user timing API. `events.dropped` says how many events were left out. A tab that shares its renderer process with another tab, such as a window its page opened, also shares the events of that process that name no frame and carry no address, for example task timing and garbage collection. The daemon allows only the timeline categories and the event transfer mode, and frees its one trace lock when the trace ends, when its tab closes and when its session ends.

Files and directories that tools save go into the `artifacts` directory next to `daemon.log`, which only you can read. An entry is named by its kind, the time and a random part, and entries older than a day are removed when a new one is saved.

## Web authentication

- `webauthn`: test passkey and security key sign-in on a tab with a virtual authenticator. One tool, chosen by `action`:
  - `add_authenticator` adds a virtual authenticator to the tab and returns its `authenticatorId`. By default it is a `ctap2` platform authenticator (`transport: "internal"`, like Touch ID) that stores discoverable credentials and verifies the user, so passkeys work. `protocol: "u2f"` makes the older security key (transport `usb`, `nfc` or `ble`, no discoverable credentials, no user verification). `residentKey`, `userVerification`, `userVerified` and `automaticPresence` (default true: every touch prompt is answered at once, since nobody is there to touch a key) tune it. A tab may have several.
  - `list_authenticators` lists the authenticators this server added to the tab. `remove_authenticator` removes one and turns the WebAuthn domain off with the last one.
  - `list_credentials` lists the credentials of an authenticator: id and user handle as base64url (the form of `PublicKeyCredential.id`), relying party id, signature counter, whether it is discoverable, user name, and backup flags. The private keys are never returned.
  - `add_credential` puts a credential into an authenticator, for a sign-in test that starts with an existing passkey: `credentialId`, `rpId` and `privateKey` (base64 of a PKCS#8 key, an ECDSA P-256 key for ES256) are required, `userHandle`, `signCount`, `residentCredential`, `userName` and `userDisplayName` are optional. `remove_credential` and `clear_credentials` remove one or all. `set_user_verified` makes the user pass or fail verification.
    Chrome lets a page use WebAuthn only on the tab that has the focus of the browser. A tab in the background fails with `NotAllowedError: The operation is not allowed at this time because the page does not have focus`, whatever the authenticator. So pass `bringToFront: true` with `add_authenticator` (it needs `allowFocus`, like `bring_to_front`) or call `bring_to_front` first; in a headless managed browser there is no window to disturb. A virtual authenticator belongs to the tab and ends when it is removed, when the domain is turned off and when the session detaches, so nothing stays behind on a tab after the client is gone. While one exists, the page cannot reach a real authenticator. The listing actions only read; every other action counts as a change, is refused in read-only mode and on a tab outside `safety.allowedDomains`.

## Web apps

- `pwa_info`: read what a tab says about being an installable web app. It only reads: nothing is installed, launched or uninstalled, and the PWA domain of the browser is not used. The result gives whether Chrome reports no problem for installing the page (`installable`), the address of the manifest, the app id and the id the manifest should declare, the manifest as Chrome parsed it (name, short name, description, `display`, orientation, start URL, scope, colors, language, icons with sizes and types, shortcuts), the problems Chrome found while parsing the manifest, the reasons Chrome would not offer to install the page (each with Chrome's id, a plain message and the values Chrome gave), and the service workers registered for the origin (scope, script and state). Secrets in the addresses of the manifest, the icons, the start URL and the workers are redacted, lists are cut (20 icons, 10 shortcuts, 10 workers) and long texts are clipped. A session that uses the `isolated` option runs in a private browser context, and Chrome then adds the problem `in-incognito` to every page, so `installable` is false there; the other problems are still the real ones. A page without a manifest gets `no-manifest` and no manifest part. Installing a web app and managing browser extensions are not part of this server.

## Behavior notes

Each emulation tool returns the full emulation state of the tab, plus what the page reports (viewport, media queries, language) when the page answers. `reset: true` removes only the overrides of that tool. Overrides live in the tab session and are gone when the tab closes or the session resets. Device emulation reports the inner size the page sees: without a viewport meta tag a mobile page keeps its default 980 CSS pixel layout width.

Input tools never bring the browser window to the front. The page believes it is focused through CDP focus emulation, enabled once per tab, so mouse and keyboard events behave like a real user while your windows stay put.

Dialog capture starts when a tab is created or selected: while a dialog is open, tools that run page scripts fail fast and name `page_dialogs` instead of timing out. The dialog policy auto-resolves later dialogs including `beforeunload` and is cleared on reset. A dialog that was already open before the tab was first created or selected cannot be observed, so `page_dialogs` cannot see or resolve it: the browser does not answer Page.enable while it is open, so the first call fails after 3 seconds with a message to resolve the dialog in the browser.

Storage tools only touch the page origin. Cookie reads never leave the page URL: no `urls` parameter is sent and `Network.getAllCookies` is never used. Cookie writes always carry the page URL, and the domain must equal the page host or be its parent domain. Values are never logged; values of local storage, session storage and cookies are only returned with `includeValues: true`.

Mock rules live per tab in the MCP process: at most 100 rules, bodies up to 10 MiB each and 64 MiB in total, delays up to 30 seconds. Requests that match no rule continue untouched. Rules survive navigation and are removed on tab close, session reset and `clear`. A `times` limit expires the rule after that many applications that were answered with the mock; a request that failed or was released unmocked does not use up the limit, and an exhausted rule is removed once its last held request is done. A request delayed by `delayMs` stays held until the delay ends. `remove` releases the requests held by the removed rule so they continue to the network unmocked, and leaves requests held by other rules alone; when the removed rule was the last one, interception is disabled. `clear` and any other disabling of interception release held requests the same way, unmocked.
