# Configuration

All settings, their flags and environment variables, defaults, precedence and the config file location.

The file is `~/.config/chromium-devtools-mcp/config.json` on macOS and Linux and `%APPDATA%\chromium-devtools-mcp\config.json` on Windows. Set `CHROMIUM_DEVTOOLS_MCP_CONFIG` to use another path. A missing file at the overridden path is an error, so a typo never silently drops your settings.

In managed mode the default `debugPort` is 0, so Chrome picks a free port at every launch and the daemon reads the real port back. The port is not predictable, which keeps the unauthenticated debugging endpoint on loopback hard to find for other local processes. The daemon stores a private identity record when it launches a managed browser and uses it to match a browser left running to the same profile directory. The port and the profile's `DevToolsActivePort` file alone cannot identify its profile. Keep the configured profile directory, its parent directories and the daemon's private files trusted during launch and reuse. On Windows the private directory inherits its access permissions. If the identity record is unavailable, close the existing managed browser before starting another daemon. This includes browsers started by versions without identity records. Set `debugPort` explicitly only when something else needs a fixed port. In attach mode the port is the fallback used to find a browser started with `--remote-debugging-port`, so its default stays 9222.

`wsEndpoint` names the exact browser to attach to, for a browser started elsewhere (another tool, a container with a published port, a script). The daemon then skips the search for a browser and connects to that address. The host must be `127.0.0.1`, `localhost` or `[::1]`, the port must be explicit and the path must start with `/devtools/browser/`; anything else is a configuration error from every source. It is an error in managed mode. The id in the address changes every time the browser starts, so after a browser restart the old address no longer works: the daemon keeps retrying, tells the client that the endpoint is unreachable and logs `could not connect to the browser yet, retrying`.

The default `profileDir` is `~/Library/Application Support/chromium-devtools-mcp/profile` on macOS, `~/.local/share/chromium-devtools-mcp/profile` on Linux and `%LOCALAPPDATA%\chromium-devtools-mcp\profile` on Windows.

`safety.allowedDomains` and `safety.deniedDomains` entries are host rules: `example.com`, `*.example.com`, `localhost:3000` or `[::1]:3000`. An entry that is not one of these forms (a URL such as `https://example.com`, a path, a bare `*`, an empty string or a host with spaces) is a configuration error from every source, the config file, the environment variable and the flag, and the installer reports it with exit code 2.

`chromium-devtools-mcp config` takes the same flags and environment variables as the server and prints the effective configuration, one line per setting with its value and the source that set it (`default`, `file`, `env` or `flag`; the last source that sets a value wins), and the path of the config file with whether it exists. An invalid file, variable or flag is reported with the field and the accepted forms and the command exits with 2; a valid configuration exits with 0. It reads nothing but the configuration, so it never starts a browser or a daemon and prints no secrets (the browser id in `wsEndpoint` is shown as `<id>`).

`tools` and `excludeTools` choose which tools the server offers, which saves context when an agent needs few of them and removes a tool completely (it is not listed and a call to it fails) instead of refusing it at call time. Entries are tool names (`click`) or groups: `tabs`, `pages`, `inspection`, `input`, `performance`, `observation`, `network`, `storage`, `webauth`, `webapps`, `emulation` and `slim`, a set of 17 tools for reading and filling pages (tabs, `page_info`, `page_navigate`, `page_wait`, `dom_snapshot`, `dom_query`, `screenshot`, `click`, `input_type`, `input_key`, `input_select`, `fill_form`, `console_logs`, `network_requests`). `tools` keeps only what it names, `excludeTools` removes from that, and a name that does not exist (also a typo) stops the server and `config` with a list of the valid names, so a tool cannot stay on by mistake. The resources `browser://tab/{tab}/...` follow the tools: `console` needs `console_logs`, `screenshot` needs `screenshot` and `text` needs one of `dom_query`, `dom_snapshot` or `a11y_snapshot`. An empty environment variable is ignored, while an empty flag (`--tools ""`) is a value and replaces the file: `tools` then offers every tool and `excludeTools` removes none. The settings belong to each client, they are not part of the daemon settings that all clients must share.

`auditLog` is an absolute path. When it is set, the server appends one JSON line per tool call, also for refused and invalid calls: `time`, `tool`, `tab`, the `url` of the tab (secrets in it replaced by `[redacted]`), `args`, `outcome` (`ok` or `error`), the `error` message (up to 300 characters) and `durationMs`. `args` is a summary, not the call: short values are kept and long ones cut, addresses are redacted, values under names that look secret (`password`, `token`, `key`, `auth`, `cookie` and the like) are `<redacted>`, and what the agent types or runs (`text`, `value`, `expression`, `html`, `promptText`) is replaced by its length and the first 12 characters of its SHA-256, so a repeated input can be recognized without being stored. The file is created with mode 0600 in a folder with mode 0700, the folder is created when it is missing, and the file is never rotated or trimmed. A write that fails is reported once on the standard error and never fails a tool call. Reading a resource is not logged.

`cdpLog` is an absolute file path for optional JSON lines containing only message direction, method, numeric request id and byte size. A sent entry means the transport accepted the message; it does not confirm delivery. Parameters, results, event data and error text are not recorded. Use a parent directory that untrusted local processes cannot modify, especially on Windows where a path can change between checks. The parent directory must exist; the file is created with mode 0600 and on macOS and Linux an existing file must not be accessible to other users. The log belongs to the shared daemon, so all clients must use the same setting. Logging failures are reported once in the daemon log and do not stop browser traffic. The file is not rotated.

Boolean env values accept `true`, `1`, `false`, `0`, case-insensitively, with surrounding whitespace ignored. An empty or whitespace-only env value counts as unset. Every boolean flag also accepts a `--no-` form, for example `--no-read-only`.

On macOS and Linux `XDG_CONFIG_HOME` overrides the directory of the config file. On Linux `XDG_DATA_HOME` overrides the directory of the managed profile; on macOS the profile always lives under `~/Library/Application Support`. On Windows `APPDATA` and `LOCALAPPDATA` play the same roles. Empty or relative values of these variables are ignored.

An unknown flag, a missing value or a stray argument is an error, so a typo never silently changes the behavior.

## Client agreement

Several MCP clients share one daemon, so some settings must match between them. See [daemon.md](daemon.md).

## Browsers

`browser` picks which browser the daemon finds, launches or attaches to: `chrome` (stable), `chrome-beta`, `chrome-dev`, `chrome-canary`, `chromium` and `edge`. Each one is looked for in its usual install locations on macOS, Windows and Linux (Chrome Canary has no Linux build) and uses its own user data directory for attach mode, so the port file is read from the right place. The error for a browser that is not found lists the locations that were checked. The locations follow the vendors' standard installs and are covered by tests with injected platforms; only stable Chrome has been run against the server. A snap or flatpak build may keep its profile elsewhere, in which case attach with `wsEndpoint` or `debugPort`.
