# Shadow DOM, frames and element ids

How element targets work across shadow roots, iframes and cross-site frames.

## Element ids

`dom_query` and `dom_snapshot` assign every element they report an id like `2_1`: the tab generation, then a counter. Pass the id as `{ "uid": "2_1" }` to target that element, or use `{ "selector": "..." }` with a CSS selector instead, never both. `pierce` and `frame` combine only with `selector`, not with `uid`. A new `dom_snapshot`, a `page_navigate` call and a navigation of the main frame start a new generation, which makes every earlier id stale. An id in a frame also goes stale when that frame navigates or is removed, while ids of other frames keep working. Using a stale id is an explicit error that asks for a new `dom_snapshot` or `dom_query`, never a wrong element. A tab keeps at most 5000 ids; the oldest are dropped first.

## Locators

A target can also be a `locator`, which finds an element the way a person describes it. Use exactly one of `uid`, `selector` or `locator`.

- `{ "locator": { "role": "button", "name": "Save" } }` finds an element by its accessibility role and accessible name, as `dom_snapshot` shows them. A text field is found by its label, `aria-label` or placeholder through its name: `{ "role": "textbox", "name": "Email" }`. The name matches a part of the accessible name and ignores case and extra spaces; pass `"exact": true` to match the whole name. Elements that are not in the accessibility tree, such as hidden ones, are not found.
- `{ "locator": { "text": "Order confirmed" } }` finds the smallest visible element whose own text contains that text, with the same matching and `exact`.
- Several matches are an error that gives the count, never a guess. Pass `nth` (counted from 0 in document order) to pick one, or make the locator more specific. No match is an error that points to `dom_snapshot`.
- `frame` combines with a locator and selects the frame to search, a locator sees open shadow roots on its own, and `pierce` does not combine with it. `name` only combines with `role`, and a locator takes `role` or `text`, not both.

## Shadow DOM and iframes

`dom_snapshot` renders the composed tree: shadow content appears inline, and every iframe shows as `[uid] iframe "name" frame=<id>` with its content as a following section; the full accessibility tree of each frame is read with the same caps, for a cross-site frame from its own session. The `frames` array of the result lists every frame with its parent, URL, `isolated` flag (true when the frame runs in its own process) and node count. At most `maxFrames` frame contents are included (default 20, maximum 50); frames beyond the limit are listed with `omitted: true`. `dom_snapshot` reads the DOM to 10 levels and the accessibility tree to 50 levels and 20000 nodes (the same node cap applies to each frame section); when a cap applies the text ends with a `[truncated: ...]` marker and `truncated` is true. Element ids inside a frame go stale when that frame navigates or is removed, while ids of other frames keep working.

Filtered `dom_snapshot` modes apply to each frame section and include matching shadow content with its available named ancestor context. A new filtered snapshot starts a new uid generation just like an unfiltered snapshot; ids remain stable within that generation. The `maxChars` limit also applies to filtered output and reports truncation.

Clicks and typing work the same across boundaries: boxes are viewport coordinates, trusted mouse events for elements in the main frame and in same-process frames are dispatched on the tab at top-level coordinates, and the hit test descends through frames and shadow roots. Cross-site frames run in their own process and are listed with `isolated: true`. Every tool that takes an element target works in them, by frame id, by iframe selector or by uid: `dom_query`, `dom_snapshot` (as `root` too), `dom_edit`, `css_inspect`, `event_listeners`, `css_edit`, `js_evaluate` with `target`, `screenshot` with `target`, `click`, `input_click`, `input_hover`, `input_scroll`, `input_select`, `input_upload`, `input_type` and `input_key`. Element work such as styles, scripting, focus, option selection and file attachment runs on the session that owns the frame, while trusted wheel and key events go through the tab, which Chrome routes into the frame. For `input_click`, `input_hover`, `screenshot` and the `css_inspect` box, a box measured in the frame is translated to page coordinates through the position and scale of each iframe element, nested frames included; the iframes are scrolled into view first, and the click hit test runs in the frame and then in each parent frame, so an element of the parent page that covers the iframe is reported. `input_click` and `input_hover` dispatch the trusted mouse events for an element inside a cross-site frame on that frame's own session, at coordinates relative to the frame's viewport, so they do not depend on how the browser routes top-level events into the frame. Before a press or hover, the tool confirms that the frame received a `mousemove` at the target point and resends it up to three times; if the frame still reports nothing, it sends the events once more through the tab at page coordinates and keeps resending for up to ten seconds. A click also confirms that the frame received the `mousedown` and repeats the press and release at most once, through the tab, if it did not, and fails with an error instead of reporting success when delivery cannot be confirmed. `input_scroll` with a target scrolls the element into view inside its frame, then scrolls the iframes into view in the page, and reports the scroll position of the frame. Sandboxed iframes without `allow-same-origin` expose no document to the debugger and cannot be queried; nested, scrolled, zero-size and `srcdoc` frames work. Frames nested inside a cross-site frame are served by the same session and get their own `dom_snapshot` sections and page coordinates.
